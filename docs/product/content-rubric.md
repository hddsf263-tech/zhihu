# 知乎经验地图｜内容评价标准

> 版本：v1.0  
> 日期：2026-09-13  
> 负责人：成员一  
> 关联文档：[PRD](./prd.md)、[用户流程说明](./user-flow.md)  
> 状态：内容质量与人工验收基线；不代表当前已有案例已经通过审核。

## 1. 文档目的

知乎经验地图的价值取决于用户能否相信两件事：路线确实来自可核对的内容，路线中的下一步确实能执行。因此，本标准规定来源、证据、路线、任务和展示文案的最低要求。

本标准用于：

- 成员二生成或保存地图前的自动校验设计；
- 成员一对主场景、备用场景和实时结果的逐条人工审核；
- 成员三判断页面必须显示哪些标签、局限和来源信息；
- 决定一个结果可以作为正式演示、只能作为开发演示，还是必须阻止展示。

本标准评价的是“基于当前可获取摘要的整理质量”，不评价答主本人，也不把整理结果当作专业、法律、医疗或投资意见。

## 2. 内容分层与展示标签

所有结果都必须区分以下四类信息，不能用同一种语气混在一起：

| 层级 | 含义 | 可使用的表达 | 禁止表达 |
|---|---|---|---|
| 来源事实 | 知乎接口返回的摘要、元数据或其中的明确陈述 | “来源摘要提到……” | 把模型概括写成答主原话 |
| 模型整理 | 根据有限摘要归纳出的路线、共同点或差异 | “基于这些摘要整理……” | 说成“知乎共识”或“所有回答都认为” |
| 产品建议 | 为了帮助执行而给出的排序、建议安排或完成判据 | “可以考虑”“建议安排” | 伪装成来源保证或成功承诺 |
| 未知/待确认 | 来源没有说明，或当前摘要不足以判断 | “资料未说明”“待核对原文” | 用常识、模型猜测或平均值补齐 |

页面应通过文案、标签、区块或引用关系让用户看出上述区别。直答模型产生的新陈述属于模型整理或产品建议，不能直接标成知乎来源事实。

## 3. 来源评价标准

### 3.1 可接受来源

v1 可使用：

1. 知乎搜索返回的内容摘要。
2. 指定知乎问题的回答摘要。
3. 知乎文章摘要。
4. 规范允许的活动故事或知识内容（如使用，必须标明其内容类型和活动范围）。

搜索结果若来自全网能力，必须单独标明全网来源，不能称为知乎来源。直答只负责整理有限摘要，不作为原始证据。

### 3.2 来源字段要求

每个来源至少保留并检查：

| 字段 | 要求 |
|---|---|
| `sourceId` | 在当前地图中唯一，并被所有引用正确关联 |
| `contentType` | 准确区分 answer、article、question_answer_summary 等类型 |
| `title` | 使用接口返回标题；缺失时使用“该问题下的回答摘要”等界面标签 |
| `authorName` | 有返回才展示；缺失显示“作者信息未返回”或隐藏 |
| `summary` | 官方接口返回的必要摘要，不扩写成全文 |
| `quoteableText` | 规范化后的可引用摘要，不能混入模型补写内容 |
| `url` | 官方知乎 URL；保留必要 UTM，不替换为非官方跳转地址 |
| `publishedAt` | 有返回才展示，缺失为未知 |
| `retrievedAt` | 记录本次获取时间，用于说明时效 |
| `authorityLevel`、`metrics` | 有真实返回才保存；不能由模型推断 |

任何来源缺少 URL、摘要或无法确认内容归属时，不得作为路线证据使用。摘要为空或仅包含无法理解的片段时，可保留为检索记录，但不能用于支撑核心行动。

### 3.3 来源去重与时效

- 同一 URL、同一内容 token 或实质相同摘要只保留一个规范化来源，避免同一内容被计为多条证据。
- 不同回答只有在策略、前提或经验内容确有差异时才分别保留。
- 必须显示生成时间、来源获取时间以及实时、缓存、演示或合成测试状态。
- 过时内容不自动判定为错误；应提示用户核对原文和时间，并在路线风险中说明时效限制。

## 4. 引用与证据评价标准

### 4.1 引用的必要条件

每条 `evidence` 必须满足：

1. `sourceId` 存在于当前地图的 `sources` 中。
2. `quote` 是对应来源 `quoteableText` 中的连续片段，不能拼接多个不连续句子。
3. 引用片段足以支持 `claim`，没有通过截断或脱离上下文改变原意。
4. `support` 准确标为 `direct` 或 `contextual`。
5. 用户可以从引用编号打开完整摘要和官方原文。

“来源说建议投递”可以是直接证据；“所以用户第 3 周一定能拿到面试”属于无来源推断，不能使用该来源支撑。

### 4.2 证据等级

| 等级 | 判定 | 可支持的内容 |
|---|---|---|
| `direct` | 摘要明确表达了与 claim 同一行动、条件或取舍 | 路线核心行动、具体步骤、明确前提 |
| `contextual` | 摘要提供相关背景，但没有直接提出该行动 | 背景说明、风险提醒、差异解释的辅助部分 |
| 不合格 | 只有主题相似、无法定位连续原文，或完全由模型补全 | 不得进入 evidence 或路线引用 |

每条路线至少需要两条来自不同内容的来源，其中核心行动至少有一条 `direct` 证据。只有一条来源时，路线必须明确标记“证据有限”，且不能为了满足数量虚构第二条来源。

### 4.3 人工引用检查

成员一检查时，应把 `quote` 在 `quoteableText` 中定位并记录：

- 是否逐字连续；
- 前后文是否改变语义；
- `claim` 是否超出原文范围；
- 是否把作者的个人经历写成普遍规律；
- 是否把产品建议误标成来源事实。

有任一项无法确认，该证据不得用于正式演示，需缩短 claim、改为 contextual，或删除该证据。

## 5. 路线评价标准

### 5.1 路线必须回答的问题

每条路线都要让用户看懂：

1. 这条路线采取什么核心策略，先做什么、后做什么。
2. 它适合什么背景、目标、时间或资源条件。
3. 需要投入什么，哪些成本或收益尚未由来源确认。
4. 主要风险是什么，什么情况会让它不再适合。
5. 用户可以从哪一项具体任务开始。
6. 哪些来源支持策略和核心行动。

### 5.2 路线合格门槛

| 检查项 | 合格标准 |
|---|---|
| 数量 | 证据足够时通常 2–3 条；证据不足时可为 1 条或 0 条 |
| 实质差异 | 策略、投入顺序、适用前提或风险存在真实差异，不只是改标题 |
| 来源数量 | 至少两条不同内容；不足时明确证据有限 |
| 核心支撑 | 核心策略和至少一个核心行动有 `direct` 证据 |
| 条件匹配 | 明确说明与用户背景、周期、投入和预算的关系 |
| 取舍 | 写出成本、风险或机会成本；来源没有数值时标为未说明 |
| 可执行性 | 有 2–5 个阶段，每阶段 1–3 个任务和可观察的完成判据 |
| 不夸大 | 不使用无来源成功率、排名、保证性结果或“唯一正确”措辞 |

路线名称应描述策略，例如“先做可展示作品”，不使用“最佳路线”“上岸最快”等未经证据支持的排名词。

### 5.3 路线差异检查示例

以下差异通常属于实质差异：

- 先做作品形成证据，再投递；与先投递获取市场反馈。
- 通过校园项目积累协作经历；与独立完成小项目形成作品集。
- 以低预算快速验证为先；与投入课程或工具换取系统学习。

以下不属于实质差异：

- 同一组任务仅更换路线标题。
- 把“先做作品”改写成“先积累作品”但步骤、条件和风险完全相同。
- 仅按回答来源拆成路线，却没有不同策略或前提。

## 6. 阶段、任务与行动清单标准

### 6.1 阶段要求

- 每条路线包含 2–5 个阶段；证据不足时可减少路线，但不能用空阶段凑数。
- 每个阶段有清晰目标和建议安排。
- “第几周”只能写作“建议安排”，不能写成来源保证的固定期限。
- 阶段顺序应能解释为什么先做某项，再做下一项；若只是并列事项，应说明并行关系。

### 6.2 任务要求

每个任务必须包含：

| 项目 | 要求 |
|---|---|
| action | 一个用户能开始执行的具体动作，避免“提升能力”等空泛表述 |
| doneWhen | 可观察的完成判据，例如产出文档、完成访谈或提交一次申请 |
| evidenceIds | 关联实际存在的证据；没有证据的产品建议需明确标为建议 |
| 建议安排 | 可选的阶段或周次，说明是产品安排而非来源承诺 |

任务不应替用户编造个人经历、作者身份、预算或结果。若任务是产品为了帮助执行而拆解的建议，页面应通过“建议”或相应标签与来源原话区分。

### 6.3 清单一致性

- 行动清单必须复用地图中已审核的阶段和任务，不在进入清单时重新生成。
- 清单中的任务、来源和完成判据要与所选 `routeId` 一致。
- 导出 Markdown 时保留任务状态、来源链接、生成时间和数据状态。
- 本机保存只记录必要的路线、taskId、完成状态和更新时间，不保存密钥或账号数据。

## 7. 用户条件与未知信息

### 7.1 条件使用

用户输入的背景、准备周数、每周投入和预算用于解释路线适配度，不代表知乎接口已按这些条件过滤内容。

审核时检查：

- 空值是否仍显示为“未指定”，没有被模型默认为零或平均值；
- 预算 `0` 是否被保留为真实零预算；
- 路线是否说明它与用户条件的关系，而不是泛泛复述回答；
- 用户条件与来源冲突时，是否呈现冲突并让用户自行权衡；
- 未提供的条件是否被标为待确认。

### 7.2 必须标记未知的内容

作者、发布时间、费用、耗时、成功率、权威等级、阅读或赞同指标等信息，来源没有返回时必须显示未知或不展示。模型不得根据上下文猜测。

以下措辞需要重点拦截：

- “保证”“一定”“成功率为……”；
- “知乎用户普遍认为……”；
- “作者是……”，但接口没有返回作者；
- “成本为 500 元”，但 500 元只是用户预算；
- “读完了全部回答”，但实际仅使用摘要。

## 8. 数据状态与时效审核

| 状态 | 允许的描述 | 必须显示 |
|---|---|---|
| 实时整理 | 本次通过服务端调用知乎能力获取并整理 | 生成时间、来源获取时间 |
| 缓存结果 | 使用已有历史快照 | 快照时间、缓存标记 |
| 演示案例 | 人工核验的预置结果 | “演示案例”，不称实时 |
| 合成测试数据 | 固定 Mock 或测试 fixture | “合成测试数据” |

审核者必须确认页面标签、导出文件和演示口播中的状态一致。实时失败后切换回放时，应明确告知已经切换到演示案例，不得保留“实时整理完成”的说法。

### 9.3 审核结论

审核结论只能取以下三种：

- **可正式演示：** C01–C20 均通过，或仅有不影响理解的文字修改已完成。
- **开发演示：** 流程可展示，但存在未核验来源、引用、状态或内容质量问题；必须在页面和口播中标明开发演示。
- **阻止展示：** 有伪造来源、断章取义、错误路线关联、密钥或敏感信息泄露，或无法判断结果是否可靠。

任何“阻止展示”项未修复前，不得把该案例作为正式 Demo、截图或参赛材料中的真实能力证明。

## 10. 自动校验与人工判断边界

### 10.1 适合自动校验

- `sourceId` 是否存在、是否唯一；
- `quote` 是否为 `quoteableText` 的连续子串；
- 路线、阶段和任务数量是否在契约范围；
- 每条路线是否关联至少两条不同来源；
- evidence 的 `support` 值和字段类型是否有效；
- URL、时间格式和必填字段是否合规；
- 结果是否包含禁止暴露的 Secret 或堆栈。

### 10.2 必须人工判断

- 引用是否断章取义；
- claim 是否超出原文语义；
- 路线之间是否有真实、可理解的差异；
- 条件与路线的适配解释是否合理；
- 任务是否足够具体且对目标用户有帮助；
- “来源事实、模型整理、产品建议、未知”是否被清楚区分；
- 页面、导出和演示口播是否造成夸大或误导。

自动校验通过不等于内容审核通过；人工判断发现问题时，以人工结论为准，并记录修改原因。

## 11. 版本与变更规则

本标准的引用、来源、路线数量、摘要边界和未知信息规则属于 v1 可信度底线。需要放宽证据门槛、改变标签含义或新增来源类型时，必须先记录 ADR，并由成员一、成员二及受影响成员评审。

仅修改路线标题、示例文案或展示顺序，可在修订记录中说明；如果改变 API 字段、ExperienceMap 结构或证据校验逻辑，应同步更新 contracts、PRD、用户流程和测试 fixture。
