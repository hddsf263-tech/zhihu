# 知乎经验地图九十秒演示稿

> 版本：v1.0  
> 负责人：成员一  
> 用途：初审和现场演示的主案例口播与操作脚本。  
> 说明：脚本中的路线名称、来源编号和时间以通过 `case-review.md` 审核的地图快照为准；示例内容不是预先核验的知乎结论。

## 1. 演示目标

让评委在 90 秒内看懂：用户已经读过多个知乎回答，却不知道如何选择；产品如何将摘要整理为可比较的多条路线；用户如何核对来源并开始执行。

演示采用主案例“大学生如何准备第一份产品经理实习？”，条件为零实习经历、8 周、每周 10 小时、预算 500 元。现场优先使用人工核验的回放案例，再用实时模式证明真实接入。回放或 Mock 必须在页面上明确标记。

## 2. 演示前检查

- [ ] 浏览器打开公网 Demo 或预载回放环境。
- [ ] 主案例回放可从首页完整走到路线、来源、清单和导出。
- [ ] 主案例 `case-review.md` 已填写并达到“可正式演示”。
- [ ] 页面显示正确的数据状态：实时整理、缓存结果、演示案例或合成测试数据。
- [ ] 来源抽屉能打开实际摘要，官方链接可在联网时新标签打开。
- [ ] 清单已有可展示的任务和完成判据，导出按钮可用。
- [ ] 不在屏幕、日志、终端、截图或视频中出现 Access Secret、Token 或其他凭证。
- [ ] 若实时服务失败，切换到回放并口头说明，不伪装成实时成功。

## 3. 主演示脚本

| 时间 | 操作 | 口播 | 评委应看到 |
|---|---|---|---|
| 0–10 秒 | 停留首页，指向输入区 | “很多人看过知乎上关于求职的回答，仍然不知道不同建议适不适合自己，也不知道第一步该做什么。知乎经验地图处理的就是收到回答之后的选择困难。” | 产品名称、口号和问题输入 |
| 10–20 秒 | 点击“填入实习示例”，检查条件 | “我用一个具体场景演示：零实习经历的大学生，用 8 周、每周 10 小时和 500 元预算准备第一份产品经理实习。” | 问题、背景、周期、时间和预算 |
| 20–30 秒 | 点击“生成经验地图”；若为回放则点击“查看已整理案例” | “系统先获取知乎可用内容摘要，再整理和检查来源。这里的阶段文案描述处理状态，不虚构分析了多少篇回答。” | 整理中四阶段或演示案例标记 |
| 30–55 秒 | 进入地图，依次指向路线卡片和比较维度 | “结果不是替用户宣布唯一答案，而是根据证据呈现可比较的路线。每条路线都说明策略、适用条件、投入、风险和阶段任务。路线数量由证据决定，页面不会为了好看硬凑三条。” | 1–3 条路线、统一比较维度、风险和任务 |
| 55–70 秒 | 点击一项任务的引用编号，打开来源抽屉 | “这项行动可以回到对应摘要和知乎原文。引用是摘要中的连续片段；作者、时间或费用没有返回时，页面会如实显示未知。” | sourceId 对应摘要、引用片段和原文入口 |
| 70–85 秒 | 点击“选择这条路线”，勾选第一项任务并点击导出 | “我选择一条路线，清单复用地图中的任务，不重新生成另一套建议。勾选状态保存在当前浏览器，也可以导出包含来源和数据状态的 Markdown。” | 所选路线、完成状态和导出文件 |
| 85–90 秒 | 指向局限说明和数据状态 | “它整理的是知乎公开内容摘要，不是全文，也不保证求职结果。用户保留选择权，产品负责把依据、取舍和下一步讲清楚。” | 局限、实时或回放状态和边界说明 |

## 4. 现场操作细节

### 4.1 首页

1. 展示首页价值说明，不先讲技术名词。
2. 点击“填入实习示例”，确认按钮只填表，不自动提交。
3. 展示条件折叠项，短暂停留在预算 500 元，说明条件用于解释适配度。
4. 提交后不要连续点击；若网络重试，沿用同一请求意图。

### 4.2 整理中

1. 让评委看到四个固定阶段。
2. 不展示虚构百分比、阅读量或模型内部推理。
3. 若使用回放，说明“这里是人工核验的演示案例，不会调用知乎或模型”。
4. 若实时超过 95 秒，停止等待并切回回放；说明实时请求未在规定时间完成。

### 4.3 地图与来源

1. 先指向问题、用户条件和数据状态，再讲路线。
2. 对路线使用“参考路线”“适用条件”“主要取舍”，避免“最优路线”。
3. 只介绍已通过审核的来源编号。
4. 打开来源抽屉后先读摘要，再展示“查看知乎原文”。
5. 如果只有一条路线，说明证据只支持一条，并不打开无意义的比较控件。

### 4.4 清单

1. 选择路线后确认 URL 中的 `routeId` 与页面标题一致。
2. 勾选一个有明确完成判据的任务。
3. 刷新一次，展示状态恢复；时间不足时可口头说明已验证。
4. 导出后打开 Markdown，展示条件、勾选状态、来源链接和实时/回放标记。

## 5. 实时失败时的备用口播

“当前实时内容服务没有在规定时间内返回，我们切换到提前核验的演示案例。这个结果明确标记为回放，不代表刚才实时请求已经成功。这样现场仍可以看到完整的路线、引用和行动清单，同时保留真实失败状态。”

切换后继续完成地图、来源和清单三步。不要说“缓存就是实时结果”，不要隐藏错误提示，不要在没有审核的实时结果上临时编造路线。

## 6. 备用案例演示

若主案例回放或实时服务不可用，回到首页输入：“独立开发者应该先做产品，还是先做内容？”

只展示经过审核的路线。备用案例的作用是证明流程适用于不同主题，不要求一定生成三条路线。如果来源不足，直接展示“证据不足”和已有来源，不把候选策略当作事实。

## 7. 演示后评委问答要点

**为什么适合知乎？** 知乎的问题聚合多种经验，回答和文章包含不同背景、策略和步骤。产品保留这些差异，并把用户从路线中的行动带回原文核对。

**是不是把回答全文交给模型？** 不是。首版只使用开放能力返回的必要摘要；摘要、模型整理、产品建议和未知信息分开显示。

**为什么不直接推荐一条最好的路线？** 用户条件和来源前提不同，系统呈现有依据的选择及取舍，把决定权留给用户。证据不足时减少路线。

**如何避免模型胡说？** 后端使用共享 schema 检查字段、数量、来源 ID 和连续引用；成员一人工核对语义和路线差异。非法输出不渲染成地图。

**为什么首版不做登录和收藏？** 先验证从问题到路线再到行动的核心闭环。登录、个人收藏和跨设备保存属于后续能力，不能成为首版使用门槛。
